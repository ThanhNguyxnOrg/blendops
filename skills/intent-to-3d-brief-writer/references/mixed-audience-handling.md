# Mixed Audience Handling

When slot 7 (Audience) lists more than one reader type (e.g. "marketing team + tech artist"), the brief must serve both without compromising plain language for the non-Blender-technical audience.

## Pattern: dual-section brief

Write the brief twice in the same file:

```md
## 1. Subject

### Plain-language version (for marketing team)
A floating cyberpunk sneaker, neon-lit, hero-centered.

### Technical version (for tech artist)
Hero subject = sneaker mesh, ~8K tris budget, hero-centered camera framing,
neon rim lighting from emission shader, glossy floor with controlled reflections.
```

Apply this dual format to slots 1, 2, 6 (the slots most affected by audience).

For slots 3, 4, 5, 7, 8 — single version is fine, written for the **strictest reader** (usually the technical one).

## Final user-facing response always plain-language

Even with a mixed-audience brief:

- The **final user-facing response** generated by `non-blender-user-response-writer` is **always plain-language only**.
- The technical version of the brief is for planners + the operator, not for the final user-facing response.

## When to split into two briefs

If the workflow truly needs two parallel deliverables (e.g. one render for marketing + one technical scene file for the artist's iteration), write **two briefs**, one per audience, with shared scope notes. Do not collapse them into one ambiguous brief.

## Anti-patterns

- Writing the brief in technical-only language because the tech artist is in the audience. Always include the plain-language version when any non-Blender-technical reader is in scope.
- Letting jargon leak into slot 6 (Acceptance criteria). Acceptance criteria are read by the user during confirmation; they must be plain.
- Forgetting that the final user response is plain-only, regardless of brief audience structure.
